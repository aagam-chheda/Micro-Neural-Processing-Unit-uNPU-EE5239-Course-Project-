# Task 012 — Top-level integration

## Goal

Build `unpu_top`, wiring together every module built so far into the
actual macro: `unpu_slave` → `unpu_csr` → (revised) `unpu_seq` →
`unpu_dma` → `unpu_wbuf`/`unpu_actbuf` → `unpu_skew`/`unpu_grid`/
`unpu_deskew` → back to `unpu_seq` for capture and writeback. This is
plan.md step 14. Every dependency (steps 1, 4, 6–10, 12, 13, and the new
13.5 `unpu_seq` revision) is done — this task is pure wiring plus a
CPU-perspective end-to-end test, no new mechanism to design. That said,
"pure wiring" across ten modules is exactly where a single swapped port
or missed connection produces a silent, hard-to-trace failure — treat
the wiring table below as load-bearing, verify it against each module's
actual current interface before instantiating.

## Files

- Create `rtl/unpu_top.sv`
- Create `tb/unpu_top_tb.sv`

## `unpu_top`'s port list

Per CLAUDE.md: "the `unpu_top` port list is negotiable, not frozen." Two
native buses, matching the interfaces already built:

```systemverilog
module unpu_top (
  input  logic         clk,
  input  logic         rst_n,

  // Native slave port -- CPU (or SPI debug backdoor) facing. Matches
  // unpu_slave's port exactly (task 010).
  input  logic [31:0]  mem_addr,
  input  logic [31:0]  mem_wdata,
  input  logic [3:0]   mem_wstrb,
  input  logic         mem_valid,
  output logic [31:0]  mem_rdata,
  output logic         mem_ready,

  // Native master port -- SRAM/arbiter facing. Matches unpu_dma's port
  // exactly (task 008).
  output logic [31:0]  dma_addr,
  output logic [31:0]  dma_wdata,
  input  logic [31:0]  dma_rdata,
  output logic [3:0]   dma_wstrb,
  output logic         dma_valid,
  input  logic         dma_ready
);
```

## Testbench (`tb/unpu_top_tb.sv`)

Drive `unpu_top` **only through its two native ports** — this is the
whole point of the test, proving the block works from a CPU's-eye view,
not by reaching into internals. Instantiate the same behavioral SRAM
model tasks 008/011 already built (word-addressable, native protocol,
randomized per-beat back-pressure) wired to the `dma_*` port. Preload it
per case from `_a.hex`/`_w.hex` at addresses **you choose per case, not
reused across cases** (stale leftover SRAM content from a previous case
masking a real addressing bug is exactly the kind of false pass to avoid
— e.g. base each case's A/W/C region on the case index).

Drive the `mem_*` port as a firmware sequence would, using the confirmed
offsets (`docs/planning/tasks/009-csr.md`): write `src_A`(0x00),
`src_B`(0x04), `dest_C`(0x08), `dim_M`(0x0C), `dim_N`(0x10), `dim_K`
(0x14), then `npu_ctrl`(0x18) **last** with bit0=START and bit1 set per
the case's MODE (`docs/planning/tasks/009-csr.md`'s polarity note: bit1=1
means signed, `mode_unsigned` output is the inverse — get this backwards
here and it's a whole-system-level repeat of the same bug task 009's
directed test already exists to catch at the CSR level, now one layer
removed). Use the **full absolute address** (`32'h4000_0000 + offset`),
not just the bare offset — this exercises `unpu_slave`'s own documented
assumption (task 010: address already window-filtered) with a realistic
address rather than a weaker 0x00-relative one. Then poll `npu_status`
(0x1C) via native reads (`wstrb=0`) until bit0 (DONE) reads 1 — a real
polling loop, not a fixed-cycle wait.

After DONE: read the model SRAM's writeback region directly (testbench-
internal inspection, not through the native port — the model memory is
testbench state) and compare to the case's `_c.hex` over the true `M×N`
submatrix.

### Directed

- **`cross_terms`** end to end through the full native-port-only path —
  the primary regression anchor, same role it's played in every prior
  task.
- **`seq_m1`/`seq_k1`/`seq_n1`/`seq_mixed`**, same path.
- **Sparse CPU-side polling**: for at least one case, poll `npu_status`
  with deliberate idle gaps between reads (mimicking a real firmware
  loop that isn't spinning every cycle) rather than back-to-back —
  confirms the integrated system doesn't depend on tight polling
  (`unpu_slave`'s own pacing-robustness was already proven standalone in
  task 010; this is a regression check that integration didn't
  reintroduce a dependency on it).
- **Illegal config through the real register path**: write an illegal
  `dim_M` (e.g. 0) via `mem_*`, pulse START, poll `npu_status` and
  confirm the ERROR bit set there (bit1, task 009's Planning-added
  status bit) matches `unpu_seq.error_code`'s value, then a legal
  case run immediately after confirms recovery.

### Plus CRV

All 64 `crv_*` cases, back to back through the same `unpu_top` instance
with no reset between them (the same no-cross-op-contamination property
task 011 proved for `unpu_seq` alone, now proven through the full native-
bus-driven path). Parse each case's `_meta.txt` (4-line format, task 006
Part A: `M=`/`MODE=`/`K=`/`N=`) to drive `dim_M`/`dim_N`/`dim_K` and
`npu_ctrl`'s SIGNED bit correctly per case — don't hardcode 64 cases by
hand. Randomize: per-case SRAM base addresses (already required above),
per-beat DMA-side back-pressure (reuse the task 008/011 model), and — new
for this task — sparse/idle-gapped CPU-side polling pacing on a random
subset of cases (extending the directed sparse-polling check into a
CRV-scale property, not just one hand-picked case). Self-check every
case against its `_c.hex`. Print the seed once (fresh draw, e.g.
`32'h5eed000c`, or your own — print whichever).

### Regression

Every existing testbench (`unpu_pe_tb` through `unpu_slave_tb` and the
revised `unpu_seq_tb`) still passes unchanged — this task touches no
existing file, so this is confirming nothing was clobbered by mistake.

## Acceptance

- All directed cases pass through the native-port-only path, including
  the sparse-polling and illegal-config-recovery checks.
- All 64 CRV cases pass, back to back, with randomized addresses,
  DMA-side back-pressure, and CPU-side polling pacing.
- Full regression green.
- Simulate clean; state which simulator (Verilator has been used the
  last six tasks — continue unless the open tooling decision in
  `docs/planning/plan.md` changes).

## Out of scope

- No firmware (`fw/`) — the testbench plays the CPU's role directly over
  the native port, not via compiled C running on a modeled PicoRV32.
  Firmware is separate, later work.
- No real arbiter RTL, no real SRAM macro — the behavioral model stands
  in for both, same as every DMA-facing testbench so far.
- No scan chain, no BIST hookup (out of scope for the whole project,
  PM-confirmed).
- Don't modify any of the ten instantiated modules.

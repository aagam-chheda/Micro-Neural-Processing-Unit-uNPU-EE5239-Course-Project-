## What the server showed (run 3, 2026-11-10 evening, PrimeTime on the ROUTE block, `UNPU_PT_TAG route`, before fill and before any antenna ECO)

- Setup, ss: 0 violating endpoints (violations file: 0). The run-1 failures (`dma_addr[31]`) are gone: ICC2 now optimises in PrimeTime's I/O convention.
- Hold, ff: `WNS -0.0238 ns, TNS -0.0667 ns, 7 violating endpoints` (ICC2's own view: -0.0004). ALL are REGISTER-TO-OUTPUT paths into `prdata[*]` (examples: `prdata[27]`, `[9]` -0.0069, `[17]` -0.0053, `[21]` -0.0029, `[12]` -0.0003; the worst two are in `pt_route/pt_hold_ff_violations.csv`). The path: launch flop in `u_csr` (`dest_c_reg_reg_*`, `src_a_reg_reg_*`, `src_b_reg_reg_*`, clocked at 0.34 to 0.38 ns) -> `QN` (`dfcrn2`) -> `oai222d1/d2` (the read mux) -> a buffer from the tool (`ctmTdsLR_*`, `buffd7`/`bufbd7`/`bufbda`) -> the port; arrival 0.99 to 1.00 against required 1.00 (= 0.50 uncertainty + 0.50 output external delay at the clk pin, zero latency). These are NOT input-to-output paths: they start at flops. The difference to ICC2 (24 ps at most) is the parasitics (SPEF vs ICC2's estimate), not a convention problem.
- Why ICC2 did not fix them: the optimisation-only margin (task 090, scope `flops`) is applied to register clock pins only, on purpose: an output-port endpoint is shared with the zero-margin `paddr` -> `prdata` group. So paths ending at output ports have no margin.

## Goal

Print and check that claim.

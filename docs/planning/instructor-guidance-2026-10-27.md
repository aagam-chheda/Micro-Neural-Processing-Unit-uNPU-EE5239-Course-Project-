## POST 1: Regarding queries on timing closure (27 Oct, 7:03 AM, General)

Dear All,

Many of you have been asking regarding how much slack should be considered good enough. For most of your cases, your WNS is positive pre-CTS, so that is fine.

### What matters at 50 MHz

- Setup is rarely the problem. With 20 ns per cycle, most paths have a lot of slack. Generous setup margins cost almost nothing, so you can keep the larger values above.
- Hold is usually the harder check. Short paths, clock skew after CTS and the fast (ff) corner cause most failures at low frequencies. Watch the hold buffer count after `final_opto` and `route_opt`.
- Don't let large setup slack hide transition problems. Max transition and max capacitance must still be clean, especially on long, lightly loaded nets.
- External or IO clocks may have far more jitter than an on-chip PLL.

TABLE: Clock period tightening by stage (50 MHz)

| Stage | Rule | 50 MHz value |
|---|---|---|
| Synthesis | 10-20% tighter period | 16-18 ns (about 55-62.5 MHz) |
| Placement / CTS | 5-10% tighter, or extra uncertainty | 18-19 ns, or +1-2 ns setup uncertainty |
| Route / signoff | Real period | 20 ns |

### 3. Clock uncertainty

For a 50 MHz clock from an on-board crystal oscillator that goes straight into the chip through an IO pad (no on-chip PLL), use about 150 ps of jitter, or 200 ps if you want a conservative value.

Where the number comes from.

TABLE: Jitter sources

| Source | Typical peak-to-peak contribution |
|---|---|
| Crystal oscillator (XO) period jitter | 30-70 ps |
| Board noise, trace crosstalk and supply noise | 20-50 ps |
| Chip IO pad and input receiver | 20-50 ps |
| Total (added linearly, which is conservative) | ~70-170 ps, so use 150/200 ps |

TABLE: Clock uncertainty by stage

| Stage | Setup uncertainty | Hold uncertainty |
|---|---|---|
| Pre-CTS | 150 (jitter) + 600 (skew) + 400 (margin) = 1.15 ns | 50 ps |
| Post-CTS / post-route / signoff | 150 (jitter) + 400 (margin) = 550 ps | 50 ps |

TABLE: WNS targets by stage

| Stage | Setup WNS | Hold WNS |
|---|---|---|
| Synthesis | >= 0 at the real 20 ns period, ideally also at 16-18 ns | Not checked (clocks are ideal) |
| Post-placement (ideal clocks) | >= -1.0 ns | Not checked |
| Post-CTS | >= -400 to -600 ps | Small violations OK; route_opt fixes them |
| Post-route (ICC2) | >= 0 (or >= -200 ps if a PrimeTime ECO follows) | >= 0 |
| Signoff (PrimeTime, ss and ff) | >= 0 | >= 0 |

- Setup WNS is usually comfortably positive at every stage, often several nanoseconds. A negative setup WNS at 50 MHz usually means a constraint problem, such as a missing multicycle path or a wrongly defined clock, rather than real logic depth.
- Hold is the check most likely to fail after CTS, especially in the ff corner. Make sure hold WNS reaches >= 0 by the end of `route_opt`.

## POST 2: Area utilisation targets (Mahima, 27 Oct, 7:22 AM, Grp_EE5239, General)

### Utilisation targets

TABLE: Healthy utilisation by stage

| Stage | Healthy utilisation |
|---|---|
| Floorplan (start) | 60-70% |
| Post-placement | <= 75% |
| Post-CTS / post-route | <= 80-85% |
| Before fillers | Whatever remains; fillers and decaps bring it to 100% |

If `report_congestion` shows overflow above about 1-2% after placement, lower the utilisation or spread the cells. Don't push on into CTS and routing with congestion that high.

The netlist grows after synthesis:

TABLE: Netlist growth added in PnR

| Added in PnR | Typical growth |
|---|---|
| Placement optimisation (sizing, buffering) | 3-8% |
| CTS buffers and inverters | 2-5% |
| Hold-fix buffers (often large at 50 MHz) | 2-5% |
| Antenna diodes, tie cells, spare cells | 1-2% |
| Total | ~10-20% |

Decaps and fillers fill leftover space, so they don't need extra area in the estimate.

## POST 3: Thumb rule for input and output delays (Mahima, 7:46 AM, date not shown, Grp_EE5239)

Here are the input and output delay rules of thumb. They're expressed as a share of the clock period T that you give to the logic OUTSIDE your design.

### 1. Default budget when nothing is known

TABLE: Input/output delay budget by situation

| Situation | Input delay (max) | Output delay (max) | Left for your logic |
|---|---|---|---|
| Default | 50% T | 50% T | 50% T |
| Generous to internal logic | 30-40% T | 30-40% T | 60-70% T |
| Slow external parts | 60-70% T | 60-70% T | 30-40% T |
| Feedthrough (input to output, no flop) | ~30-35% T each | ~30-35% T each | ~30-40% T |

Min delays, for hold:
- Input delay min: about 5-10% T, or the fastest external clock-to-output time plus board delay.
- Output delay min: about 0-5% T, or the minimum board delay minus the external hold time.

### 2. By interface type

TABLE: Rule of thumb by interface

| Interface | Rule |
|---|---|
| Chip-level IO to a board device | Use the datasheet when you have it: input = Tco + board delay; output = Tsu + board delay. Otherwise use 50% T. |
| Block-level in an SoC, neighbour has a flop at its port | Input or output delay of about 20-30% T, since only the wire and a few gates are outside. |
| Block-level, neighbour has logic at its port | About 60-70% T. The neighbour uses most of the cycle, so your side gets 30-40%. |
| Two blocks sharing one cycle with no knowledge of either | Split it 50/50, keeping about 10% T aside for top-level wiring. |
| Asynchronous IO (resets, slow control) | Don't time it with IO delays. Use a synchronizer plus `set_false_path` or `set_max_delay`. |

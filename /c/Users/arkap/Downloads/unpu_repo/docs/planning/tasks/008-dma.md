# Task 008 — DMA master

## Goal

buffers built in task 007 (`unpu_actbuf`, `unpu_wbuf`), plus a source for
writing `C` back out. This covers plan.md steps **10 and 11** together —
they share the same two files and step 11 (randomized back-pressure) is

## The native memory-interface convention (already settled, quoted for reference)

From `docs/session-handoff.md` §4/§5 and the decisions table: the DMA↔SRAM
port is PicoRV32's native memory interface. `wstrb==0` means read;
`dma_rdata` is valid the same cycle as `valid & ready`; **the address
advances only on cycles where `dma_valid` and `dma_ready` are both
high** — incrementing on `valid` alone silently skips words and is, per
the notebook (§07 7.2), "the classic DMA bug... wrong in a way no
waveform makes obvious." We are higher-priority than the CPU at the
arbiter (PM-confirmed) but no latency number was given — back-pressure is
expected and must never cause a hang (§2's SPI-backdoor-slowness
constraint applies to us too, even though that's really about the slave
side).

## The bus handshake FSM — the notebook's own 4-state design (quoted)

```
D_IDLE  dma_valid=0                    dma_req -> D_REQ; load base addr, beat count
D_REQ   dma_valid=1, addr, wstrb       dma_ready -> D_ACK; else hold everything stable, stay
D_ACK   capture dma_rdata / retire write   beats remaining -> D_REQ (addr+4); else -> D_FIN
D_FIN   dma_done=1 for one cycle       -> D_IDLE
```
Build this version, not the "collapse D_REQ/D_ACK" tuned version the
notebook also mentions — `docs/session-handoff.md` §6 decisions table is
explicit: "Build the 4-state DMA FSM first, optimise later — Collapsed
version is much harder to debug while the arbiter is also under test."

This task's `unpu_dma` reuses this exact 4-state loop as its **per-beat**
core, looped once per SRAM word, plus one additional state (`BUF_LOAD`)
to drain a fetch into `unpu_actbuf`/`unpu_wbuf`'s load port once all beats
of a fetch are in. That's not a deviation from "4-state" — it's the
necessary wrapping for a "beat" to become a multi-beat "job" (a whole
tensor, not one word), which is what plan.md step 10 actually asks this
block to do.

## Addressing convention — Planning's choice, not yet firmware-confirmed

`docs/session-handoff.md` §7 item 5 lists "SRAM memory layout" as
deliberately unfilled pending the MNIST network-shape decision. `unpu_dma`
needs *something* concrete to fetch/write against now. This is that
something — flagged as Planning's convention, revisit if firmware ends up
wanting a different one:

- **`A` (M×K) and `W` (K×N): one 32-bit SRAM word per row, always, padded
  to 4 bytes regardless of real K/N.** Matches the notebook §06 bandwidth
  argument ("one 32-bit SRAM word feeds exactly one cycle of the array")
  literally, and needs no runtime multiply for addressing:
  `addr(row i) = base + i*4`. Fetch exactly `M` words for `A`, `K` words
  for `W` — real K/N never change *how many* words are fetched for A/W,
  only what `unpu_actbuf`/`unpu_wbuf` do with the bytes inside each word
  (their own masking from task 007 already handles K<4/N<4 correctly
  regardless of what garbage sits in an unfetched row's stage slot).
- **`C` (M×N): fixed 4-word (16-byte) row stride, one word per column,
  always** — `addr(row m, col j) = dest_C + m*16 + j*4` — but **only the
  real `N` words per row are actually written** ("only write back the
  real N columns," `docs/session-handoff.md` §6). This needs explicit
  row/column counters, not a flat running address (going from column
  `N-1` of row `m` to column `0` of row `m+1` is not a `+4` step whenever
  `N<4`) — this is exactly the "M/N/K-aware addressing... not just a flat
  M-row stream" plan.md step 10 asks for.
- Byte order within a fetched word: `load_row[i] = dma_rdata[8*i +: 8]`
  (byte 0 = bits `[7:0]` = column/row-element 0). State this in the file
  header if you pick something else, but this is the convention every
  other convention in this project already reads little-endian-ish
  against, so don't reinvent it without a reason.

## `unpu_dma` interface

```systemverilog
module unpu_dma (
  input  logic                  clk,
  input  logic                  rst_n,

  // Native master port to (arbitrated, shared) SRAM
  output logic [31:0]           dma_addr,
  output logic [31:0]           dma_wdata,
  input  logic [31:0]           dma_rdata,
  output logic [3:0]            dma_wstrb,      // 4'h0 = read; 4'hF = write (no partial writes in this design)
  output logic                  dma_valid,
  input  logic                  dma_ready,

  // Job control -- one job at a time, latched (shadow copy) at job_start
  input  logic                  job_start,        // 1-cycle pulse; sampled only in D_IDLE
  input  logic [1:0]            job_kind,         // 2'd0 = fetch A, 2'd1 = fetch W, 2'd2 = writeback C
  input  logic [31:0]           job_base_addr,    // src_A / src_B / dest_C
  input  logic [2:0]            job_m,            // 1-4
  input  logic [2:0]            job_n,            // 1-4
  input  logic [2:0]            job_k,            // 1-4
  output logic                  job_busy,
  output logic                  job_done,         // 1-cycle pulse

  // Fetch-A output -- wire straight into unpu_actbuf's load port
  output logic                  a_load_start,
  output logic [2:0]            a_load_m,
  output logic [2:0]            a_load_k,
  output logic [3:0][7:0]       a_load_row,

  // Fetch-W output -- wire straight into unpu_wbuf's load port
  output logic                  w_load_start,
  output logic [2:0]            w_load_k,
  output logic [2:0]            w_load_n,
  output logic [3:0][7:0]       w_load_row,

  // Writeback-C source -- shaped exactly like unpu_seq's c_dst, so step
  // 14 can wire this directly. Purely combinational read from DMA's side.
  input  logic [3:0][3:0][31:0] c_src
);
```

## FSM

`D_IDLE`, `D_REQ`, `D_ACK`, `BUF_LOAD`, `D_FIN` — `enum`, synthesisable
subset.

- **`D_IDLE`** — `dma_valid=0`, `job_busy=0`. On `job_start`: latch
  `job_kind`/`job_base_addr`/`job_m`/`job_n`/`job_k` into shadow copies;
  `beat_idx<=0`; `cur_m<=0`; `cur_j<=0`; `total_beats <=`
  (`job_kind==FETCH_A ? m_lat : job_kind==FETCH_W ? k_lat : m_lat*n_lat`)
  → `D_REQ`.
- **`D_REQ`** — `job_busy=1`, `dma_valid=1`.
  - `dma_addr = (job_kind==WRITE_C) ? base_lat + cur_m*16 + cur_j*4 : base_lat + beat_idx*4`
  - `dma_wstrb = (job_kind==WRITE_C) ? 4'hF : 4'h0`
  - `dma_wdata = (job_kind==WRITE_C) ? c_src[cur_m][cur_j] : don't-care`
  - `dma_ready` high → `D_ACK`. Otherwise **hold every output exactly as
    driven this cycle and stay in `D_REQ`** — this is what "matching the
    native convention" means operationally: a slow/absent grant must
    never corrupt or advance anything.
- **`D_ACK`** — one cycle. If not a write: `stage[beat_idx] <= dma_rdata`
  (a 4-entry, 32-bit staging array — this is the "16 bytes of registers"-
  scale buffer that absorbs arbiter back-pressure so the downstream
  buffer-load burst in `BUF_LOAD` can be clean and gap-free, since
  `unpu_actbuf`/`unpu_wbuf`'s load protocol from task 007 expects 4
  back-to-back cycles with no stalls once `load_start` fires — do not try
  to feed them directly off the bus beat-by-beat). Advance counters:
  `beat_idx <= beat_idx+1`; for `WRITE_C`, also advance `cur_j`/`cur_m`
  (`cur_j==n_lat-1` → `cur_j<=0, cur_m<=cur_m+1`, else `cur_j<=cur_j+1`).
  If `beat_idx == total_beats-1`: → `D_FIN` for `WRITE_C`, else →
  `BUF_LOAD`. Otherwise → `D_REQ`.
- **`BUF_LOAD`** — only reached for `FETCH_A`/`FETCH_W`. Exactly 4 cycles,
  `ld_cnt` 0..3:
  - `FETCH_A`: `a_load_start` pulsed on `ld_cnt==0` (natural order, row
    0 first — matches `unpu_actbuf`'s spec). `a_load_row = (ld_cnt <
    m_lat) ? unpack(stage[ld_cnt]) : '0`. `a_load_m=m_lat`,
    `a_load_k=k_lat` held throughout.
  - `FETCH_W`: `w_load_start` pulsed on `ld_cnt==0`, **carrying row 3
    first** — `unpu_wbuf` requires reverse order (task 007). Present
    `w_load_row = (row_idx < k_lat) ? unpack(stage[row_idx]) : '0` where
    `row_idx = 3 - ld_cnt`. Rows that were never fetched (`row_idx >=
    k_lat`) get `'0` here, but this is belt-and-suspenders — `unpu_wbuf`
    already zero-masks by `load_k` internally (task 007), so it's fine
    even if this were garbage. `w_load_k=k_lat`, `w_load_n=n_lat` held
    throughout.
  - On `ld_cnt==3` → `D_FIN`.
- **`D_FIN`** — `job_done=1` for one cycle, `job_busy=0` → `D_IDLE`.

**Known trap, carried forward from the notebook and from task 007's own
lesson**: don't let any output (`dma_addr`, `a_load_row`, etc.) depend on
a registered state/counter in a way that's one cycle stale on the exact
cycle it needs to be fresh (task 007 hit exactly this with `weight_in`
vs. `active_sel` on the swap cycle). Check every `BUF_LOAD`-cycle output
against the *current* `ld_cnt`/`row_idx`, not last cycle's.

## Testbench (`tb/unpu_dma_tb.sv`)

Instantiate `unpu_dma` + `unpu_actbuf` + `unpu_wbuf` (fetch outputs wired
to their load ports, matching task 007's port names) + a small behavioral
SRAM model you write inline: a word-addressable array, responding to
`dma_valid`/`dma_addr`/`dma_wstrb`/`dma_wdata` with `dma_ready` and (for
reads) `dma_rdata` valid the same cycle `ready` is asserted — per the
convention above. Preload it from the `_a.hex`/`_w.hex` vector files at a
chosen base address (pack 4 bytes per SRAM word, matching the addressing
convention above) for fetch tests; read it back after a writeback test
and compare against `_c.hex`.

### Directed

- **Fetch A + fetch W for `cross_terms`** (M=K=N=4): run both jobs against
  the preloaded model SRAM, `swap` both buffers (testbench pulses `swap`
  directly, same role it played in task 007), and verify correctness two
  ways: (a) read `unpu_actbuf`'s active bank back via its `rd_row` port
  and compare to `cross_terms_a.hex`; (b) feed `unpu_wbuf`'s
  `weight_load`/`weight_in` into a `unpu_grid` instance and run a known
  activation pattern through it (or reuse the whitebox `stage[col][row]`
  check from task 007's own testbench) to confirm the weights landed in
  the right rows — this is also your regression check that DMA's
  `BUF_LOAD` reverse-order presentation to `unpu_wbuf` didn't reintroduce
  the row-settling bug task 007 already solved once.
- **Writeback C for `cross_terms`**: drive `c_src` with `cross_terms`'s
  known `C` values, issue a `WRITE_C` job, read the model SRAM back at
  the expected `m*16+j*4` offsets, compare to `cross_terms_c.hex`.
- **`seq_k1`/`seq_n1`/`seq_mixed`** through both fetch and writeback,
  proving the addressing convention's K/N-awareness (fetch beat counts
  driven by real K/M only; writeback beat count and row stride driven by
  real N).
- **Held-back-pressure directed case**: force `dma_ready` low for a fixed
  multi-cycle stretch mid-job (both during a fetch and during a
  writeback) and confirm `dma_addr`/`dma_valid`/`dma_wdata` hold exactly
  stable across the stall (no silent address advance — the classic bug
  the notebook names explicitly) and the job still completes correctly
  once `ready` returns.

### Plus CRV (steps 10 and 11 together)

Iterate the 64 `crv_*` cases. For each: fetch A and W from the model
SRAM (preloaded per-case), verify via `unpu_actbuf`/`unpu_wbuf` as above;
writeback C and verify against `_c.hex`. **Randomize, per the plan.md
CRV methodology and step 11's back-pressure requirement:**
- burst length and address — already covered by iterating all 64 cases
  (random M/K/N) at randomized base addresses (don't reuse the same
  `job_base_addr` every iteration; pick a fresh one per case)
- **arbiter grant latency/back-pressure** — the model SRAM should hold
  `dma_ready` low for a random 0-5 cycle delay before granting *every*
  beat, not just a directed stall, drawn from a seeded PRNG
- confirm no job ever hangs and no result is ever corrupted, across all
  64 cases

Print the seed once at the top (new draw, e.g. `32'h5eed0008` — pick one,
print whichever). Self-check every case against the golden vectors.
